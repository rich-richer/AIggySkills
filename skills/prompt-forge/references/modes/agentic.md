# Agent 模式（Agentic）

> 什么时候读这个文件：要让 AI 用工具自己干活——改代码、查资料、跑命令、操作软件、连续多步完成任务，而不是只回一段文字。
> 读完你会得到：一个"目标—权限—确认点—工作方式—停止条件"的 Agent 提示词骨架，一张必问清单，一个填好的编码代理示例，以及防止它跑飞的四道闸。

## 什么时候用

- 用户会这样说："帮我把这个功能改好""你去把这几份文件整理一下""你自己看着办，做完给我看结果"。
- 任务需要**多步执行 + 工具调用**：读写文件、跑命令、调 API、点网页，单轮回答不够。
- 任务有副作用：会改代码、会发消息、会花钱、会动数据。
- 用户愿意（或必须）为每一步负责，所以需要知道 AI 做了什么、为什么。
- 需要判断"什么时候该停"，而不是无限往下做。

## 骨架

```
# 任务：在 {{仓库／环境}} 里完成 {{目标}}

## 背景
- 环境：{{Next.js 15 单体仓库，约 6 万行，12 人维护}}
- 为什么做：{{客服每周手工导出 3 次数据，每次 40 分钟}}
- 相关位置（我自己找过的）：{{app/reports/page.tsx、lib/export.ts}}
- 你不需要先读整个仓库：先 grep 关键词定位，再读相关文件

## 你的权限
- 可以改：{{app/、lib/、tests/}}
- 不要改：{{package.json 依赖、数据库 migration、CI 配置}}——要改先问我
- 可以运行：{{npm test、npm run lint、npm run build}}
- 不要运行：{{任何部署命令、任何删库／清缓存的命令}}

## 工作方式
1. 先读再计划：读完相关文件后，用 10 行以内说清"改哪几个文件、怎么验证"，等我回"可以"再动手
2. 一次只做一步：每步结束说清楚改了什么、跑了什么命令、结果如何
3. 遇到不确定的接口或字段：先去代码里找定义；找不到就问我，不要猜
4. 不许留"TODO 以后补"：要么做完，要么明确说没做
5. 每完成一个可交付阶段就存一条笔记到 {{NOTES.md}}（做了什么／验证到哪／还剩什么），别靠记忆

## 必须停下来问我的情况
- 要删文件、改数据库结构、加依赖
- 要访问仓库以外的系统（线上环境、第三方 API、付费服务）
- 同一个错误试了 2 次还没解决
- 你觉得我的需求本身有矛盾

## 停止条件与预算
- 预算：{{30 分钟 / 20 次工具调用}}；到期没完成就汇报进度，不要硬撑
- 完成定义：{{npm test 全绿 + 导出的 CSV 能被 Excel 打开 + 我在浏览器点一次能下载}}
- 不允许用"降级方案"偷偷绕过验收（比如不写测试就算完成）

## 交付
- 改动清单：文件 + 一句话理由
- 一个可回滚的提交，分支名 {{feat/export-csv}}，不要直接改 main
- 3 条我在本地验证的命令 + 预期输出
```

## 必问信息

| 编号 | 问题 | 为什么必须问 | 缺省假设 |
|---|---|---|---|
| I-A1 | 有哪些工具和环境可用（文件、终端、浏览器、API、哪些能连）？ | 权限边界是 Agent 提示词的第一句；不给边界它会"顺手"改依赖 | 默认只能读写当前工作目录、只能跑测试与构建，不能部署 |
| I-A2 | 哪些操作必须先问你？ | 不可逆操作要留人工闸门；事后补救的成本远高于事前确认 | 默认删文件、改表结构、加依赖、花钱、对外发消息一律先问 |
| I-A3 | 什么算完成、什么算该停（时间／次数／连续失败）？ | 没有停止条件的 Agent 会无限试错，还会把失败包装成"基本完成" | 默认同一错误 2 次不过就停；预算 30 分钟或 20 次调用 |
| I-G2 | 成功标准是什么？能不能用**可执行的检查**表达（测试、lint、脚本）？ | 能确定性验证的任务优先接确定性检查，而不是"再问一遍模型"（验证器优先于投票器） | 默认"测试通过 + 我手动点一次能用" |
| I-G3 | 绝对不能碰什么（生产库、客户数据、别人的分支）？ | Agent 的破坏半径取决于你写没写这条 | 默认禁止碰生产环境与客户数据，禁止直接改主干分支 |
| I-G5 | 有没有已有材料：相关文件、旧 PR、报错日志、复现步骤？ | 上下文越具体，它越少瞎找；最小高信号 token 优于整库塞入（见 `../techniques/context-engineering.md`） | 默认先给 3–5 个相关路径 + 1 段报错 |
| I-G4 | 一次性执行，还是要做成长期可复用的代理（写进 system prompt）？ | 长期代理要沉淀稳定规则（本 skill 不提供长期人设模板） | 默认一次性任务，任务结束即止 |
| I-F2 | 要不要先让它只做"读 + 计划"给你看？ | 计划是成本最低的人工闸门，看完再放行执行 | 默认先出 10 行计划，等确认 |

## 组装规则

1. **上下文工程优先于措辞。** 只给"最小高信号 token 集合"：3–5 个相关文件路径 + 一段报错 + 验收命令；不要指望把整库塞进提示词就能解决问题（context rot 与 lost-in-the-middle 已证伪，见 `../anti-patterns.md`）。
2. **权限分层写死：可以改／不要改／可以跑／不要跑。** 四行必须都有，缺一行就少一道闸。
3. **人工闸门只留 4 个：** 删、改结构、花钱、对外。太多闸门会让你变成点确认的机器，太少会翻车。
4. **停止条件必须可数。** "尽量做好"不是条件；"同一错误 2 次不过就停""30 分钟到期就汇报"才是。
5. **长任务用外部笔记，不靠记忆。** 让它在 `NOTES.md` 里记进度（做了什么／验证到哪／还剩什么），跨会话也能续（见 `../techniques/context-engineering.md`）。
6. **说目标，不指定工具与步骤。** 写清要达成什么、约束和验收即可；不要写「先用 A 工具再用 B 工具」。简短口令（如 `commit, push, PR`、「查一下 git 历史」）模型能自己补全约定（Boris Cherny 演讲）。
7. **给它能自己运行的反馈，并要求迭代。** 单元测试、集成测试、截图（Puppeteer、模拟器）、设计稿对照——有了「看见结果」的途径，第一版「还不错」，迭代两三次常能「接近完美」。提示词里写明：`完成后运行 {{检查}}，不通过就继续改，直到 {{验收标准}}`。
8. **开头点明工作流（三选一）。** ① 探索 → 计划 → 确认 → 写码 → 提交（需求未定）；② 写测试 → 提交 → 迭代（对错可由测试判定）；③ 写码 → 截图看结果 → 迭代 → 提交（界面与视觉交付）。
9. **告诉它有哪些工具。** 团队 CLI 写名字和用途，让它用 `--help` 自学；MCP 工具写用途。常用的写进项目级 CLAUDE.md 或 `.mcp.json`，不要每次在提示词里重复。
10. **常驻上下文要短，反复纠正要固化。** CLAUDE.md 只放常用命令、架构决策、关键文件、风格约定；同一个纠正出现第二次，就写进 CLAUDE.md 或做成斜杠命令，而不是每次加长提示词（见 `../techniques/context-engineering.md`）。
11. **交付六件套**（按 SKILL.md 的六件套交付）：任务提示词、变量说明、一句用法（在仓库根目录开新会话）、2 条纠偏话术、1–3 条 eval（含"绕过验收算完成即不合格"的反例）、模型适配备注。

## 填好的示例

```
# 任务：在 admin 后台加"导出订单 CSV"功能

## 背景
- 环境：Next.js 15 单体仓库，约 6 万行，12 人维护；测试用 Vitest
- 为什么做：客服每周手工从三个页面抄数据做报表，每次约 40 分钟
- 相关位置（我自己找过的）：app/admin/orders/page.tsx、lib/orders.ts、tests/orders.test.ts
- 你不需要先读整个仓库：先 grep "orders" 和 "csv" 定位，再读相关文件

## 你的权限
- 可以改：app/admin/、lib/、tests/
- 不要改：package.json 依赖、prisma/schema.prisma、.github/workflows/——要改先问我
- 可以运行：npm test、npm run lint、npm run build
- 不要运行：任何 deploy 命令、任何 prisma migrate、任何 rm -rf

## 工作方式
1. 先读再计划：读完相关文件后，用 10 行以内说清"改哪几个文件、怎么验证"，等我回"可以"再动手
2. 一次只做一步：每步结束说清楚改了什么、跑了什么命令、结果如何
3. 遇到不确定的字段名或接口：先去代码里找定义；找不到就问我，不要猜
4. 不许留"TODO 以后补"：要么做完，要么明确说没做
5. 每完成一个可交付阶段就追加一条笔记到 NOTES.md（做了什么／验证到哪／还剩什么）

## 必须停下来问我的情况
- 要删文件、改数据库结构、加依赖
- 要访问线上环境或第三方付费 API
- 同一个错误试了 2 次还没解决
- 你发现"按当前数据结构导不出客户要的字段"这类需求矛盾

## 停止条件与预算
- 预算：30 分钟 / 20 次工具调用；到期没完成就汇报进度，不要硬撑
- 完成定义：npm test 全绿 + 我点一次"导出"能下到 CSV + 该文件用 Excel 打开中文不乱码
- 不允许用降级方案偷偷绕过验收（例如跳过测试、把筛选条件写死）

## 交付
- 改动清单：文件 + 一句话理由
- 一个可回滚的提交，分支 feat/export-orders-csv，不要直接改 main
- 3 条我在本地验证的命令 + 预期输出
```

**这段为什么这样写：** "相关位置（我自己找过的）"把搜索空间压到 3 个文件，比贴一整棵目录树省 token 也省时间；"不许用降级方案绕过验收"是针对 Agent 最常见的作弊路径——把没做完说成"基本完成"；停止条件写成"30 分钟 / 20 次调用"两个可数指标，是为了让它在失控前自己停下。

**两条纠偏话术：**
- "停一下。你刚才跳过了计划直接改了 4 个文件，其中 tests/ 的改动没有说明理由。回到第 1 步：先给我 10 行计划，说明为什么每个文件都要改。"
- "你说'测试基本通过'，把 npm test 的完整输出贴出来，包括失败的用例名；如果有失败，不许改测试断言来让它通过。"

**两条 eval case：**
- ✅ 合格：先给计划再动手；改动集中在允许目录；`npm test` 输出全绿；提交在 `feat/export-orders-csv` 分支且能 revert。
- ❌ 不合格：为了让测试通过而修改已有测试断言，或直接改 `package.json` 加依赖没问——判不合格，回滚该提交并重来。

## 模型适配

- **推理模型：** 只给目标、权限、验收命令、停止条件；**不要**写"先列 5 步计划再执行"当成思考脚手架（见 `../models.md` 的模型分叉表）。但"先输出 10 行计划等我确认"是**流程闸门**，不是思维链，可以保留。
- **通用聊天模型：** 权限四行 + 一步一汇报 + 停止条件，是最稳的组合。Claude 用 XML 分区（`<permissions>` `<stop_conditions>`）；Gemini 给一条"合格的一步汇报"样例。
- **小模型／本地模型：** 一次只给一个文件级任务，砍掉"自主计划"，改成"我逐步喂你，你只做当前这一步"，并强制每步输出 diff。
- **迁移提醒：** 换 Claude 4.6+ 删掉 prefill 续写；换 Gemini 4 补 few-shot、删 temperature；换 OpenAI 推理模型删掉"一步步想"，改用 reasoning effort（见 `../models.md` 的模型分叉表）。

## 常见坑

1. 不要写"你自己看着办，做完给我"——没有权限边界和停止条件，就等于把仓库交给一个不知道哪里不能碰的人。
2. 不要一次塞 10 个需求——拆成一个可验收的阶段一个任务；任务越大，它越倾向"糊一个能跑的版本"。
3. 不要让"测试全绿"成为唯一验收——同时要有人能点一次的真实路径（浏览器点一次能下载），否则它会把功能藏在测试里。
4. 不要允许它自己加依赖、改表结构——这两件事的连锁成本最高，必须留人工闸门。
5. 不要用"你是资深架构师"来替代权限说明——角色设定对事实与推理没有增益（见 `../anti-patterns.md` 的已证伪清单）。
6. 不要长会话不带笔记——上下文会漂移；要求它每阶段写 `NOTES.md`，你也能据此接手（见 `../techniques/context-engineering.md`）。
7. 不要一句话丢一个三千行级别的大功能——先要计划或拆阶段，否则它可能做出完全不是你要的东西。
8. 不要逐步指挥工具调用——写目标、约束和验收；指挥步骤既费字又会挡住它找到更好的路径。

## 自检

- [ ] 权限四行（可改／不可改／可跑／不可跑）都写了吗？
- [ ] 有人工闸门清单（删、改结构、花钱、对外）吗？
- [ ] 停止条件是可数的（时间／次数／连续失败）吗？
- [ ] 完成定义里有至少一条人手动能验证的路径？
- [ ] 有"绕过验收即不合格"的反例 eval 吗？
- [ ] 有它自己能运行的反馈手段（测试／截图／脚本），并要求迭代到通过吗？
