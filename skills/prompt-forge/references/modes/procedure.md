# 操作模式（Procedure）

> 什么时候读这个文件：要写一份别人能照着做、卡住能自己解决的软件操作／配置／排错步骤（SOP），而不是一段"操作说明"。
> 读完你会得到：一个"环境—步骤—验证—失败分支—回滚"的 SOP 骨架，一张必问清单，一个填好的完整示例，以及让新手不卡在第一步的四条硬规则。

## 什么时候用

- 用户会这样说："写个教程教我同事装这个""这个报错怎么修""帮我把流程写成 SOP""配一下这个软件"。
- 读者是**不完美的执行者**：不懂代码、不在你旁边、会漏看一行、会点错按钮。
- 步骤涉及不可逆操作（删文件、改配置、付费、发版），错了要走回滚。
- 环境有版本差异：同一个菜单在不同版本里位置不同，写"最新版"必翻车。
- 同一件事会被重复做（每周、每个新人入职），所以值得沉淀。

## 骨架

```
# 操作 SOP：{{任务名}}

## 环境（不确定就写"待核实"，不要猜）
- 系统：{{Windows 11 23H2 ／ macOS 14.x ／ Ubuntu 22.04}}
- 软件与版本：{{Python 3.12.x、VS Code 1.9x}}
- 账号权限：{{普通用户 ／ 需要管理员}}
- 前置条件：{{已装 Git、能连公司 Wi-Fi、磁盘剩 5GB}}
- 不适用的情况：{{版本低于 X 的不要按这份做，先升级}}

## 读者是谁
{{完全不会写代码的运营同事，共 5 人，每人独立操作，我不同时在旁边}}

## 输出格式
Markdown 编号步骤。每一步固定写四行：
- 做什么：一句祈使句
- 在哪做：菜单路径／命令行（写完整路径，不要写"设置里"）
- 怎么验证成功：看到什么界面、什么输出、什么提示
- 失败了怎么办：最常见的 1 个报错 + 一句处理办法

## 规则
- 一步只做一件事；能点按钮就不要写命令
- 涉及删除／覆盖／付费的步骤，前面加 ⚠️，并写"先备份什么"
- 版本可能有差异的地方，标"（版本可能不同，待核实）"，不要编一个路径
- 不要写"根据实际情况调整"——给具体默认值
- 命令要能整行复制，不要夹中文注释

## 结尾
- 一页纸检查清单（可打勾）
- 卡住时可以发我的 3 样东西：第几步、报错原文截图、当前界面截图
```

## 必问信息

| 编号 | 问题 | 为什么必须问 | 缺省假设 |
|---|---|---|---|
| I-O1 | 环境：什么系统、什么软件、什么版本？谁有管理员权限？ | 版本差异是 SOP 失效的第一大原因；菜单路径几乎每个大版本都变 | 默认 Windows 11 + 普通用户权限，版本号一律要求用户补，缺则标"待核实" |
| I-O2 | 失败了怎么办：能重装吗？能回滚吗？谁负责处理？ | 有回滚和没回滚，SOP 的写法完全不同（后者要先备份） | 默认"可回滚、按备份恢复"，不允许静默跳过 |
| I-G1 | 谁照着做？他懂多少？几个人、同时做还是各自做？ | 给程序员的 SOP 给运营用，会死在第一个命令行 | 默认非技术同事、各自独立操作、无人在旁 |
| I-G2 | 什么样算成功？最后要看到什么？ | 没有终点验证的 SOP 是"操作记录"不是 SOP | 默认以"屏幕上出现预期结果"为验收，并要求截图 |
| I-G3 | 有哪些绝对不能碰（生产库、客户数据、系统设置）？ | 新手最危险的是"顺手点了不该点的" | 默认禁止改系统环境变量、禁止动已有数据文件 |
| I-G4 | 交付形态：打印版、在线文档、还是要贴进知识库？ | 打印版要更短、在线版可以带链接 | 默认在线 Markdown，≤25 步 |
| I-F2 | 要不要先写一个"只到第一步"的试跑版？ | 最贵的浪费是写了 30 步才发现环境写错 | 默认先出"环境 + 前 3 步 + 验证方式"给你试 |

## 组装规则

1. **验证点是 SOP 的命门。** 每一步都必须能回答"怎么知道这步成功了"；写不出验证点的步骤，说明你还没想清楚它在做什么。
2. **失败分支只写最高频的那 1 个。** 穷举所有报错会让文档变成废墟（也让模型开始编）；一个高频报错 + 一句处理，比 10 条臆测的报错有用。
3. **不确定性必须显式标注。** 菜单路径、包名、默认端口这类会随版本变的东西，不确定就写"（待核实）"，绝不编一个看起来对的路径（这条没有例外）。
4. **顺序：环境 → 步骤 → 每步验证 → 回滚 → 检查清单。** 环境段放在最前面，读者第一眼就能判断"这份 SOP 是不是给我的"。
5. **长度：单任务 ≤25 步。** 超过就拆成两份 SOP（准备篇 / 执行篇）；步子太碎会让新手反复确认自己是否漏看。
6. **交付六件套**（按 SKILL.md 的六件套交付）：SOP 正文、变量说明、一句用法、2 条追问话术、1–3 条 eval（含"没有验证点即不合格"的反例）、模型适配备注。

## 填好的示例

```
# 操作 SOP：让 5 位运营同事在自己电脑上跑通"读 Excel 出汇总"的脚本

## 环境（不确定就写"待核实"，不要猜）
- 系统：Windows 11 23H2
- 软件与版本：Python 3.12.x、VS Code 1.9x（版本号以实际装到的为准，路径可能略有差异）
- 账号权限：普通用户，不需要管理员（安装时如果弹 UAC 选"是"）
- 前置条件：能连公司 Wi-Fi、D 盘剩余 2GB、已有一个 Excel 文件（示例：9 月销售明细.xlsx）
- 不适用的情况：系统是 Windows 10 或公司电脑禁装软件的，不要按这份做，先找 IT

## 读者是谁
完全不会写代码的运营同事，共 5 人，每人独立操作，我不同时在旁边。

## 输出格式
Markdown 编号步骤。每一步固定写四行：
- 做什么：一句祈使句
- 在哪做：菜单路径／命令行（完整路径）
- 怎么验证成功：看到什么界面、什么输出
- 失败了怎么办：最常见的 1 个报错 + 一句处理办法

## 规则
- 一步只做一件事；能点按钮就不要写命令
- 涉及删除／覆盖／付费的步骤，前面加 ⚠️，并写"先备份什么"
- 版本可能有差异的地方标"（版本可能不同，待核实）"，不要编路径
- 不要写"根据实际情况调整"，给具体默认值
- 命令要能整行复制，不要夹中文注释

## 结尾
- 一页纸检查清单（可打勾）
- 卡住时发我 3 样东西：第几步、报错原文截图、当前界面截图
```

**这段为什么这样写：** "不适用的情况"这一段是新手 SOP 最常漏的——把"Windows 10 别按这份做"写出来，能挡掉一半的求助；"失败了就发我 3 样东西"把求助成本压到最低，也避免你在群里来回问"你到哪一步了"；"命令要能整行复制"是针对新手真实死法的规则（多半死在手动输入时少了一个字符）。

**两条追问话术：**
- "第 4 步的验证方式写得太虚（'安装成功即可'）。改成具体能看到的界面或命令输出，并给一句对应的期望文字。"
- "如果这一步失败了、同事又判断不出来，他应该回到第几步重做？把回滚路径补进每一节的末尾。"

**两条 eval case：**
- ✅ 合格：每一步都有"做什么／在哪做／怎么验证／失败怎么办"四行；环境段写了版本和不适用情况；含 1 处 ⚠️ 备份提醒。
- ❌ 不合格：出现"点击设置里的相关选项"这类模糊路径，或某一步没有验证方式——判不合格，退回重写该步。

## 模型适配

- **推理模型：** 给环境、读者、输出格式和验证要求，不要写"先规划再输出"。它容易补全你没给的细节，所以"不确定标待核实"必须写进规则（见 `../models.md` 的模型判断规则）。
- **通用聊天模型：** 四行格式 + 一条完整样例步骤，比形容词有效。Claude 用 `<environment>` `<reader>` 分区；Gemini 给 2 条"好的步骤 vs 坏的步骤"示例。
- **小模型／本地模型：** 只允许写"环境 + 8 步以内 + 每步 1 行验证"，不要失败分支（它会开始编报错）；复杂排错单独再问一次。
- **图像／视频模型：** 不适用；需要截图讲解时，把"屏幕上应该看到什么"写成文字描述，不要要求模型生成假界面截图。

## 常见坑

1. 不要写"安装好即可"——没有验证点，新手不知道自己装没装上。
2. 不要写"最新版"——写具体版本号；版本不明就标"（待核实）"，让读者自己去核对。
3. 不要穷举 10 个报错——只写最高频的 1 个；其余留给"卡住时发我 3 样东西"。
4. 不要漏掉回滚和备份——涉及删除、覆盖、付费的步骤必须前置 ⚠️（可回滚是承诺，不是选项）。
5. 不要假设读者有管理员权限——权限不足是新手上门求助的第一大原因。
6. 不要把 3 个操作塞进一步——一步只做一件事；步骤少而清楚，比步骤多而"完整"有用。
