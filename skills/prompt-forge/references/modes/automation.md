# 自动化模式（Automation）

> 什么时候读这个文件：要把 AI 塞进一条会自动跑的工作流里——Make／n8n／Zapier 的节点、API 调用、定时任务，输出要被下一个节点直接消费。
> 读完你会得到：一个"触发器—节点—变量映射—输出契约—兜底—上线测试"的自动化提示词骨架，一张必问清单，一个填好的邮件分拣示例，以及让路由器不走错分支的三条规则。

## 什么时候用

- 用户会这样说："帮我搭个自动分拣邮件的流程""这个节点提示词怎么写""每天定时生成一份日报推到群里"。
- AI 的输出不是给人读的，而是给**下一个节点**读的：路由器、数据库、消息推送。
- 流程会无人值守地跑几百次，一次格式错就可能污染整批数据。
- 需要参数化：同一条流程要处理不同主题／不同客户，而不是复制 5 份。
- 有失败场景：接口超时、返回空、返回了枚举外的值。

## 骨架

```
# 工作流：{{每日 8:00 邮件分拣}}

## 这条流水线做什么
{{触发器}} → {{分类节点}} → {{路由器}} → {{摘要节点}} → {{推送}}
一次运行处理 {{≤20}} 条；单条失败不阻塞整批。

## 每个节点的输入输出（写死，不要跨节点猜变量）
| 节点 | 输入变量 | 输出 | 下游怎么消费 |
|---|---|---|---|
| 分类 | {{1.Body.Content}} | 单个词：重要／推广／其他 | 路由器按"全文等于"匹配 |
| 摘要 | {{1.Body.Content}} | ≤60 字纯文本 | 飞书消息正文 |
| 推送 | {{4.text}} | 无 | 三个群按类别分开 |

## 分类节点提示词
你是邮件分类器。只输出"重要""推广""其他"三个词中的一个。
不要标点、不要解释、不要换行。
邮件正文：{{1.Body.Content}}

## 输出契约
- 只输出枚举内的一个值；多一个字，路由器就走错分支
- 不要输出 markdown、冒号、引号
- 不确定时输出"其他"（宁可漏判，不要错判到"重要"）
- 摘要节点：纯文本，不带"摘要："前缀，不换行

## 变量与参数化
- 场景变量：{{prompt_topic}}、{{prompt_tone}}，不要把同一条流程复制 5 份
- 变量映射示例：邮件正文 {{1.Body.Content}}、上游聚合 {{4.text}}、场景输入 {{var.input.topic}}
- 不要在提示词里写死只在测试环境成立的值（测试邮箱、日期、固定姓名）

## 失败兜底
- 节点报错：重试 1 次；仍失败 → 走"其他"分支并记录原文
- 输出不在枚举内：当失败处理，**不要**用模糊匹配硬接
- 空输入：直接走"其他"，不要调用模型
- 频控：每小时最多 {{20}} 条，超出排队，不并发

## 上线前测试
给我 5 条测试输入（3 条典型 + 1 条空 + 1 条完全无关），并给每条的期望输出。
```

## 必问信息

| 编号 | 问题 | 为什么必须问 | 缺省假设 |
|---|---|---|---|
| I-W1 | 变量从哪来：哪个触发器的哪个字段？字段名是什么？ | 变量名写错是自动化最常见的"静默失败"：流程跑通但内容全空 | 默认变量写成平台原生格式（如 `{{1.Body.Content}}`），并让用户核对字段名 |
| I-W2 | 输出给谁消费：路由器？数据库？消息？它对格式有多严格？ | 同一句话，给人读可以宽松，给路由器读必须逐字匹配 | 默认接路由器与消息推送，要求"只输出枚举值" |
| I-G4 | 跑在哪个平台（Make／n8n／Zapier／自建 API）？模型是哪个？ | 平台决定变量语法和重试机制，模型决定能不能用结构化输出 | 默认 Make 风格变量 + 通用聊天模型 |
| I-O2 | 失败了怎么办：重试几次、走哪个分支、要不要告警？ | 无人值守的流程必须自带兜底，否则错一次你三天后才发现 | 默认重试 1 次，失败走"其他"分支 + 记录原文 |
| I-E1 | 分类枚举是哪几个？有没有兜底类目？ | 枚举不闭合，路由器迟早收到第四个值 | 默认 3 类 + "其他"兜底 |
| I-G2 | 怎么算跑对了？有历史数据可以回放测试吗？ | 工作流无法"看着改"，只能用样例回放验证 | 默认用 5 条样本（含空输入与无关输入）回放 |
| I-E3 | 每次跑多少条、多久跑一次、token 预算多少？ | 频次和条数决定要不要批处理、用哪个档位的模型 | 默认每小时 ≤20 条，单条 ≤800 token |

## 组装规则

1. **一个节点只做一件事。** 把"分类 + 摘要 + 抽标题"塞进一个节点，输出就无法被路由器逐字匹配；拆成三个节点，每个都有明确的输出契约。
2. **凡是给路由器消费的输出，一律闭合枚举 + 兜底。** 只输出一个词、不给标点、加"其他"兜底；不确定时走兜底而不是猜。
3. **变量映射写全并参数化。** 每个节点标清"输入来自哪个模块的哪个字段"，变量名（如 `{{1.Body.Content}}`、`{{var.input.topic}}`、`{{4.text}}`）一个字符都不能错；主题、语气、客户名抽成场景变量（Axton《重构个体》6.2.3 参数化），一条流程服务多个场景，不复制多份。
5. **兜底分支必须存在且可观测。** 失败不是"再来一次"，而是"去哪个分支、谁收到告警、原文存在哪"。
6. **先回放测试，再上线。** 5 条样本里必须有 1 条空输入和 1 条无关输入——这两条最能暴露枚举与兜底的问题。
7. **交付六件套**（按 SKILL.md 的六件套交付）：节点提示词、变量说明、一句用法（贴进哪个节点）、2 条纠错话术、1–3 条 eval（含"输出带解释文字导致路由器走错分支即不合格"的反例）、模型适配备注。
8. **Claude Code 无头模式（`claude -p`）当节点用时**：把它当成「聪明的 Unix 工具」——提示词自带全部上下文（管道输入或指明要读的文件）；用允许工具列表限定它能做什么（可细到具体 bash 命令）；指定 `--output-format json`（或 `stream-json`），下游用 `jq '.result'` 之类取值；写清什么算完成、失败时输出什么。例：`git status | claude -p "what are my changes?" --output-format=json | jq '.result'`（Boris Cherny 演讲；参数以当前官方文档为准）。

## 填好的示例

```
# 工作流：每日 8:00 邮件分拣（Make）

## 这条流水线做什么
Gmail 触发器（新邮件）→ AI 分类节点 → Router（3 分支）→ 摘要节点 → 飞书群推送
每天约 180 封，每小时处理 ≤20 条；单条失败不阻塞整批。

## 每个节点的输入输出
| 节点 | 输入变量 | 输出 | 下游怎么消费 |
|---|---|---|---|
| 分类 | {{1.Body.Content}} | 单个词：重要／推广／其他 | Router 按全文等于匹配 |
| 摘要 | {{1.Body.Content}} | ≤60 字纯文本 | 飞书消息正文 |
| 推送 | {{4.text}} | 无 | 重要→投研群；推广→运营群；其他→归档频道 |

## 分类节点提示词
你是邮件分类器。只输出"重要""推广""其他"三个词中的一个。
不要标点、不要解释、不要换行。
判断规则：
- 重要：发件人是真人、内容要求我方回复或决策、含截止时间
- 推广：营销、订阅、促销、活动通知
- 其他：系统通知、自动回复、无法判断
邮件正文：{{1.Body.Content}}

## 摘要节点提示词
用不超过 60 字总结这封邮件的核心诉求，写成一句话。
只输出正文，不要"摘要："前缀，不要换行，不要加表情。
邮件正文：{{1.Body.Content}}

## 输出契约
- 分类节点：只输出枚举内的一个词，多一个字 Router 就走错分支
- 摘要节点：纯文本、单行、≤60 字
- 两个节点都不许输出 markdown、引号、冒号、列表符号

## 变量与参数化
- 分类与摘要共用一个"判断口径"变量 {{var.input.category_rule}}，换团队时不改提示词
- 变量映射：邮件正文 {{1.Body.Content}}、上游聚合 {{4.text}}、场景输入 {{var.input.topic}}
- 不要写死测试邮箱或固定日期

## 失败兜底
- AI 模块报错：重试 1 次；仍失败 → 走"其他"分支，把原文写进归档表格
- 输出不在枚举内：当失败处理，不要模糊匹配（"重要。"也算失败）
- 空正文：直接走"其他"，不调用模型
- 每小时 >20 条：排队，不并发

## 上线前测试
给我 5 条测试输入（3 条典型 + 1 条空 + 1 条完全无关），并给每条的期望输出：
1. 投资人问"周五前能否给到数据" → 重要
2. "双十一会员 8 折" → 推广
3. （空正文） → 其他
4. "系统将于今晚 2:00 维护" → 其他
5. "我们合同里的付款条款能改吗" → 重要
```

**这段为什么这样写：** 分类节点的输出去掉所有标点，是为了让 Router 能用"全文等于"精确匹配，而不是靠模糊包含；"重要"的判断规则写成"真人 + 要回复/决策 + 有截止时间"三条可勾选条件，比写"判断重要性"稳定；空正文单独一条兜底，是因为空输入是自动化里最常见的真实故障。另外注意：示例里的 `{{1.Body.Content}}`、`{{4.text}}`、`{{var.input.topic}}` 是平台变量映射，不是待填的空槽位。

**两条纠错话术：**
- "Router 昨天有 7 封邮件掉进'其他'，检查分类节点是不是输出了带句号的'重要。'。把契约改成'只输出三个字，不要任何标点'，并把重试后的分支改成记录原文。"
- "摘要节点偶尔输出两行。把输出契约改成'只允许一行、不超过 60 字、不允许换行符'，并加一条空输入的期望输出。"

**两条 eval case：**
- ✅ 合格：分类输出严格是 `重要`／`推广`／`其他` 之一（无标点、无空格、无换行），Router 三个分支都能命中，空正文不走模型直接归档。
- ❌ 不合格：输出 `类别：重要` 或 `这封邮件属于重要`——Router 匹配失败，判不合格，进兜底分支并修提示词。

## 模型适配

- **分类这种"只输出一个词"的节点：** 用便宜、快的通用聊天模型即可，**不要用推理模型**——为三个字花一轮深度思考，成本和延迟都不划算（经验规则）；推理模型只留给需要判断的节点（如"这封投诉是否需要升级"），且给判断规则而不是思维步骤。
- **摘要、改写这类节点：** 通用聊天模型足够；Claude 用 XML 包住输入，Gemini 给 2 条"正文 → 一句话摘要"的样例。
- **小模型／本地模型：** 只做二分类或单字段抽取，枚举砍到 2–3 个；兜底分支必须存在，因为小模型更常输出枚举外的值。
- **平台差异：** Make 的变量语法是 `{{1.Body.Content}}` 这种模块序号形式，n8n／自建 API 用表达式或 JSON 字段名（不同平台写法不同，以平台文档为准）。

## 常见坑

1. 不要在一个节点里做三件事——分类、摘要、抽标题混在一起，输出就没法给路由器逐字匹配。
2. 不要把自然语言丢给路由器——路由器只认闭合枚举，所以提示词必须写"只输出一个词，不要标点"。
3. 不要让模型自己决定路由——让模型只做分类，路由交给平台的 Router／Switch 节点；模型只管"是什么"，平台管"去哪"。
4. 不要忘记空输入——空正文是自动化最高频的真实故障，必须有一条"不调用模型直接走兜底"的规则。
5. 不要在提示词里写死测试环境的值（测试邮箱、固定日期、某个人名），也不要把 API key 写进提示词——密钥放平台的凭证管理，提示词只放业务规则。
6. 不要不测试就上线——用 5 条样本回放（含空输入与无关输入），比看一遍提示词有用十倍。
