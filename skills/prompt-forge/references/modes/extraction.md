# 抽取模式（Extraction）

> 什么时候读这个文件：要把一堆非结构化内容（工单、标题、会议记录、网页正文、发票）变成 JSON、标签或表格，并且要被程序或 BI 直接消费。
> 读完你会得到：一个"字段定义 + 枚举 + 未知值 + 格式契约"的抽取骨架，一张必问清单，一个可以直接抄的填好示例，以及能用脚本验的三条硬检查。

## 什么时候用

- 用户会这样说："把这些评论打上标签""从这 800 条工单里抽字段""转成 JSON 我要导进表格"。
- 输出要被**程序消费**：导入 BI、写数据库、塞进自动化节点——错一个字段就整批废。
- 输入量大、格式杂乱、有大量缺失值和表达不一致（"退款""退钱""要退"是同一件事）。
- 需要分类而不是生成：类别有限且必须闭合。
- 用户已经有一批人工标过的样本，可以拿来做验收。

## 骨架

```
# 抽取任务：{{任务名}}

## 输入
- 输入类型：{{客服工单正文／商品标题／会议记录／网页正文}}
- 一次处理：{{50}} 条，每条用一个标签包住：<item id="1">……</item>
- 原文里没有的信息，按"未知值规则"处理，不许猜

## 输出形状（必须完全一致）
只输出一个 JSON 数组。不要前言、不要解释、不要 markdown 代码围栏。
[
  {
    "id": "1",
    "category": "退款|物流|质量|发票|账号|其他",
    "urgency": 1,
    "product": "字符串或 null",
    "refund_requested": true,
    "summary": "≤30 字，中文，不出现『客户表示』"
  }
]

## 字段定义
| 字段 | 类型 | 允许值 | 判断规则 |
|---|---|---|---|
| category | 枚举 | 六类之一 | 按诉求主张归类；一条工单有多种诉求时，取"客户最想解决的那一个" |
| urgency | 整数 | 1／2／3 | 3=今天必须回复；2=48 小时内；1=其余 |
| product | 字符串 | 原文出现过的产品名 | 原文没提就 null，不要用"未知" |
| refund_requested | 布尔 | true／false | 只有明确提到退款／退钱／补偿才算 true |
| summary | 字符串 | ≤30 字 | 只写事实，不写情绪，不写建议 |

## 未知值规则
- 原文没有的信息一律 null，不要推断，不要写"未知""待补充"
- 同一字段有两种理解时，选更保守的那个，并把该条放进"confidence": 0.5
- 字段全部缺失时，category 给"其他"，其余 null

## 格式约定（重要）
- 字符串双引号，布尔 true/false，不要用"是／否"
- 数组顺序必须与输入 id 顺序一致
- 只输出 JSON；看到任何中文解释，整批作废重跑
- 数字不要加千分位，不要写成字符串

## 交付前自查
- 我给的 id 数量 = 你输出的对象数量？
- 有没有出现枚举以外的 category？
- 有没有把 summary 写成 30 字以上？
```

## 必问信息

| 编号 | 问题 | 为什么必须问 | 缺省假设 |
|---|---|---|---|
| I-E1 | 要抽哪些字段？每个字段的枚举值或格式是什么？ | 字段定义含糊是抽取失败的第一原因；枚举不闭合，标签体系会越跑越脏 | 默认先跑 20 条让模型提候选枚举，确认后再批量 |
| I-E2 | 原文没写这个字段时怎么处理——null、空字符串还是"未知"？ | 三种处理方式在 BI 里是三种结果，混用会污染统计 | 默认 null，且绝不推断 |
| I-E3 | 输入规模与分批方式：总共多少条、一次喂多少？ | 条数决定要不要分批、要不要写重试；一次 500 条必然漏行 | 默认每次 50 条，按 id 区间切批 |
| I-G2 | 成功标准是什么？有没有人工标好的 20 条样本？ | 有金标样本就能验收，没样本就只能靠肉眼抽查 | 默认用 20 条人工样本做验收，准确率目标 ≥95%（经验阈值，按业务调） |
| I-G4 | 下游是谁消费？模型支持不支持结构化输出（structured outputs）？ | 支持结构化输出时不需要用"必须输出 JSON 否则……"的强措辞（见 `../anti-patterns.md` 的已证伪清单） | 默认接 BI 看板，按纯 JSON 数组交付 |
| I-G3 | 哪些情况必须判"其他"，哪些词一出现就升级紧急？ | 兜底类目和升级词是业务规则，模型猜不出来 | 默认给"其他"兜底；敏感词（投诉监管、律师、报警）一律 urgent=3 |
| I-F1 | 我把字段、枚举、未知值规则复述一遍，有没有要改的？ | 批量任务返工代价最高，先对齐定义再跑 | 默认按已给定义开跑 20 条试标 |

## 组装规则

1. **先小样本定型，再批量。** 拿 20 条跑一遍，把模型自造的枚举值收回来、把边界案例写进字段定义，再放开批量（经验规则，非实测但极其省返工）。
2. **枚举必须有兜底类目。** 六类 + "其他"；没有兜底，长尾内容会被硬塞进现有类别，标签体系越跑越脏。
3. **有 structured outputs 就用，不要用强措辞求格式。** "必须输出 JSON，否则……"在支持结构化输出的模型上属于噪音（见 `../anti-patterns.md`：不再需要用强措辞获得一致格式）。
4. **分批 + 幂等。** 每批带 id 区间，失败只重跑该批；要求"数组顺序与输入一致"，才能在合并时对齐。
5. **显式声明格式约定。** 同一个提示词里写死引号、布尔写法、不加千分位——单个分隔符字符的变化就能造成输出波动（见 `../anti-patterns.md`：单个分隔符字符可致 ±23% 波动），写清楚能显著提稳。
6. **交付六件套**（按 SKILL.md 的六件套交付）：提示词、变量说明、一句用法、2 条修错话术、1–3 条 eval（含"输出带解释文字即不合格"的反例）、模型适配备注；额外给一份"校验脚本思路"。

## 填好的示例

```
# 抽取任务：客服工单结构化

## 输入
- 输入类型：客服工单正文（用户在 App 内提交的一手文字，含错别字与口语）
- 一次处理：50 条，每条用一个标签包住：<item id="1">……</item>
- 原文里没有的信息按"未知值规则"处理，不许猜

## 输出形状（必须完全一致）
只输出一个 JSON 数组。不要前言、不要解释、不要 markdown 代码围栏。
[
  {
    "id": "1",
    "category": "退款|物流|质量|发票|账号|其他",
    "urgency": 1,
    "product": "字符串或 null",
    "refund_requested": true,
    "summary": "≤30 字，中文，不出现『客户表示』"
  }
]

## 字段定义
- category：按诉求主张归类；一条工单有多种诉求时，取"客户最想解决的那一个"
- urgency：3=今天必须回复（含"投诉到监管""律师""报警"等词）；2=48 小时内；1=其余
- product：原文出现过的产品名，原文没提就 null
- refund_requested：只有明确提到退款／退钱／补偿才为 true
- summary：只写事实，不写情绪，不写建议，≤30 字

## 未知值规则
- 原文没有的信息一律 null，不推断，不写"未知""待补充"
- 同一字段有两种理解时，选更保守的那个，并给该条 "confidence": 0.5
- 字段全部缺失时，category 给"其他"，其余 null

## 格式约定（重要）
- 字符串双引号，布尔 true/false，不要用"是／否"
- 数组顺序必须与输入 id 顺序一致
- 只输出 JSON；看到任何中文解释，整批作废重跑

## 交付前自查
- 我给的 id 数量 = 你输出的对象数量？
- 有没有出现六类以外的 category？
- 有没有 summary 超过 30 字？
```

**这段为什么这样写：** 字段规则里"取客户最想解决的那一个"是唯一能消解多诉求工单歧义的写法，比写"按实际情况判断"可执行；把"投诉到监管""律师"直接列成升级词，是为了让 urgency 可被人工复核；"看到任何中文解释整批作废"是给下游脚本的一道保险。

**两条修错话术：**
- "第 7 条和 19 条的 category 判成了'质量'，但原文只要求补发配件，没有质量主张。重跑这两条，并说明你的判断依据，只输出 JSON。"
- "你这次输出的数组只有 48 个对象，输入是 50 条。找出漏掉的两个 id，补齐后重新输出整批。"

**两条 eval case：**
- ✅ 合格：50 条输出 50 个对象、id 连续、category 全在六类内、summary 全部 ≤30 字；含一条全字段缺失的工单时，输出为 `{"id":"33","category":"其他","urgency":1,"product":null,"refund_requested":false,"summary":"内容为空"}`。
- ❌ 不合格：输出前面带"好的，以下是抽取结果："，或把"退钱"判成 refund_requested=false——判不合格，整批重跑。

## 模型适配

- **推理模型：** 不要给"先理解再归类"的步骤；给 schema + 判断规则 + 3 条边界样例即可。任务越机械，越不要让它自由推理（见 `../models.md` 的模型判断规则）。
- **通用聊天模型：** Claude 用 `<item>` 包输入、把 schema 放最前面；Gemini **总是给 few-shot**，2–3 条"原文 → 期望 JSON"的样例比规则描述有效。
- **小模型／本地模型：** 字段砍到 3–4 个、枚举砍到 3 类、每次 20 条；示例给 4 条以上并把格式写得死板；不要让它输出嵌套 JSON。
- **参数与迁移：** 不要靠调 temperature 求稳定——OpenAI 开推理后必须移除 temperature、Claude 4.7+ 传非默认值直接 400、Gemini 4 直接忽略（见 `../models.md` 的模型分叉表）。换模型时删掉所有 prefill 续写技巧，改用结构化输出或 system 指令。

## 常见坑

1. 不要写"请尽量准确地抽取"——改成可枚举的字段定义 + 未知值规则。
2. 不要给开放枚举——枚举不闭合，标签只会越跑越脏；一定留"其他"。
3. 不要用"必须输出 JSON，否则我会惩罚你"这类强措辞——有 structured outputs 就直接用（见 `../anti-patterns.md` 的已证伪清单）。
4. 不要一次塞 500 条——会漏行且无法定位；50 条一批、带 id 区间、失败只重跑该批。
5. 不要假设模型知道你的业务词（"改地址""补发"算哪类）——把边界案例写进字段定义。
6. 不要只在聊天窗口看结果——**能确定性验证的任务优先接脚本校验**（JSON 可解析、枚举合法、条数一致），比"再问一遍模型"可靠（验证器优先于投票器）。
