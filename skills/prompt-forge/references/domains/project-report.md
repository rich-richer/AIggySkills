# 项目与商业报告（Project & Business Reporting）

**什么时候读这个文件**：用户要写的是「给组织里的人看、并且要推动一个动作」的文档——周报、立项、复盘、结项、商业计划书、路演材料。
**读完你会得到**：报告类文档必须锁死的 8 个参数、3 种主力体裁的骨架、对外材料的合规红线，以及一个填好的立项报告提示词。
**分工**：论证结构与篇幅控制见 `../modes/report.md`；结论先行、金字塔结构属于技法层，本文件只写报告这个行业特有的口径与合规。

## 什么时候用

- 用户会说：「写个周报/月报」「做个立项报告」「写 BP」「帮我复盘这个项目」「结项材料怎么写」。
- 读者是老板、客户、投资人、跨部门同事，文档要换资源（钱、人、时间）或换授权（签字、排期）。
- 用户手里有一堆过程材料和截图，要先决定「哪些进文档、哪些不进」。
- 用户说「随便写写就行」但文档会进正式流程（审批、投标、对外）——按正式标准写，别按随便写。

## 行业参数

| 维度 | 必须问到 | 用户不答时的默认 | 采访编号 |
|---|---|---|---|
| 读者与决策权 | 谁签字、谁只是想知情、谁会反对 | 直属上级是唯一决策者 | `I-P1` |
| 文档目的 | 要钱 / 要人 / 要批准 / 对齐信息 / 对外融资 | 对齐信息 + 要一个明确批准 | `I-P1` |
| 项目阶段 | 立项前 / 进行中 / 结项 / 复盘 | 进行中，写阶段汇报 | `I-G1` |
| KPI 与口径 | 用哪些指标、怎么算、统计周期 | 沿用用户现有指标，不新造指标 | `I-P2` |
| 数据来源 | 系统导出 / 手工台账 / 估算，可信度如何 | 只有用户口头给的数字，标注「未核实」 | `I-G5` |
| 敏感信息边界 | 客户名、预算、内部代号、未发布计划能否出现 | 脱敏，客户写「某连锁餐饮客户」 | `I-G3` |
| 篇幅与载体 | 一页纸 / Word / PPT / 邮件正文；有没有模板 | 一页纸 + 附件 | `I-G4` |
| 时效与节点 | 什么时候要交、汇报多长、是否需要预读 | 本周内交付，汇报 10 分钟 | `I-G2` |

## 常用体裁 × 3

### 1. 阶段汇报（周报 / 月报 / 双周报）

```
【一句话状态】{{项目}} 当前 {{正常/预警/阻塞}}，因为 {{最关键的那一个事实}}。
【本期结果】对比上期计划的 {{3–5}} 项，逐项写：计划 → 实际 → 差异 → 原因。
【风险与阻塞】{{风险}}｜影响 {{范围/时间/金额}}｜需要谁在 {{日期}} 前做什么。
【下期计划】{{3–5}} 项，每项带交付物与负责人。
【需要老板决策】只在真有决策时写：{{选项 A/B}}，我建议 {{A}}。
```

适合谁：需要让上级 60 秒内判断「要不要介入」的项目负责人；也是 `../modes/report.md` 里最短的形态。

### 2. 立项报告 / 商业论证（Business Case）

```
【要批准什么】预算 {{金额}} + 人力 {{人数}}，批准后 {{起止时间}} 交付 {{结果}}。
【问题】不做的代价是 {{可量化损失}}，证据是 {{数据来源}}。
【方案】主方案 + 备选方案各 3 行；为什么选主方案（成本/速度/风险）。
【投入产出】一次性投入 {{}}、每月运营成本 {{}}、回收周期 {{}} 个月，假设逐条列出。
【风险与兜底】{{3}} 个主要风险 + 触发信号 + 止损线（到 {{指标}} 就停）。
【不做范围】本期明确不做的 {{}}，避免被追加需求。
```

适合谁：要说服老板或投委会批预算的人；核心不是「项目多好」，而是「判断错了损失可控」。

### 3. 复盘报告（Retrospective）

```
【目标 vs 结果】原定 {{目标 + 数字}}，实际 {{结果 + 数字}}，差距 {{}}。
【关键事实时间线】{{5–8}} 个决定性节点，每条只写事实与时间，不写评价。
【归因】分三层：外部环境 / 决策质量 / 执行质量；每层给证据。
【可复用资产】沉淀成 {{SOP / 模板 / 检查清单}}，谁来维护。
【下次改什么】{{3}} 条，每条必须能改（「需求评审加一个验收标准检查项」），不能是「加强沟通」。
```

适合谁：项目刚结项或刚失败、要写「组织记忆」的人；写给自己团队看，比写给老板看更有价值。

## 术语与合规边界

**必用术语（首次出现给中英对照）**

- 结论先行（BLUF, Bottom Line Up Front）/ 金字塔原理（Pyramid Principle）：先结论、再分组理由、最后事实。
- 里程碑（milestone）、工作分解结构（WBS）、挣值管理（EVM）、关键路径。
- 投资回报率（ROI）、回收期（payback period）、总拥有成本（TCO）、假设（assumption）与情景（scenario）。
- 风险登记册（risk register）：风险、概率、影响、责任人、触发信号、应对。
- 干系人（stakeholder）、范围蔓延（scope creep）、定义完成（DoD, Definition of Done）。

**合规红线**

- **数字必须带口径与期间**：写「Q1 转化率 12%（口径：注册→付费，2026-01 至 2026-03）」，不写「转化率提升明显」。
- **估算和实际要分开标**：估算写「预估（假设见下）」，不能写成已发生。
- 对外材料（BP、路演、投标）：不出现内部代号、未公开客户名、员工个人信息；客户 logo 与案例需授权。
- 对投资人：不得承诺收益或确定性增长，预测必须标「基于 X 假设」；财务材料加「不构成投资建议」。
- 不编造已签约客户、订单、专利、奖项——宁可少写，不能假写。
- 内部人事、法务争议不进周报正文，走正式渠道（细则见 `./workplace-communication.md`）。

## 填好的示例

场景：给运营总监写一份「门店自助点餐机」立项报告，申请 18 万预算。数字可替换。

```
你帮我写一份立项报告，读者是运营总监（周五审批会，10 分钟阅读，会问「多久回本、错了怎么办」）。
语气：结论先行、给数字、不用形容词堆形容词。

## 事实素材（只用这些，不要补充你没看到的数据）
- 现有 12 家门店，午餐高峰平均排队 9 分钟，客诉中「等太久」占 31%（2026-09 至 2026-10 客服台账）。
- 试点 1 家门店装 2 台自助点餐机 4 周：单均点餐时间从 3.2 分钟降到 1.6 分钟，试点店午市单量 +8%，但客单价 -1.2 元。
- 设备报价：2 台 3.6 万元/店（含安装）；SaaS 服务费 400 元/店/月；需 1 名兼职运维 0.5 人月/月。
- 计划首批 5 家门店，预算 18 万元（设备 18 万含 5 店设备，服务费另计）。

## 报告结构
1. 一句话结论：建议批准 18 万元，在 5 家门店试点 90 天，达标再全量。
2. 问题与不做的代价（用上面的客诉与排队数据，写清口径与期间）。
3. 试点证据（4 周数据 + 它不能证明什么：样本只有 1 家店，客单价下滑原因未查清）。
4. 投入产出：一次性投入、月度运营成本、回本路径；把「单量 +8%」和「客单价 -1.2 元」两个方向都算进去，给出保守/中性两档。
5. 风险与止损线：设备故障、员工抵触、客单价继续下滑；写明触发信号与止损动作。
6. 不做范围：本期不做会员打通、不做外卖渠道改造。
7. 需要总监决策的 3 个点（含「是否接受先只上 3 家店」的备选）。

## 格式
Markdown，一页半以内；所有数字标注口径与期间；估算标明「预估」；不要写「赋能」「抓手」「闭环」这类词。
```

> 这段为什么这样写：把「读者会追问什么」写进提示词（多久回本、错了怎么办），模型才会主动给止损线；明确「试点数据不能证明什么」，是为了防止报告把 1 家店的样本当结论；正负两个方向的数据都要求算进去，避免只报好消息。
> 换模型：小模型/本地模型把结构压到 4 段、每条给一个填空示例；Gemini 4 建议补一个「合格立项报告开头」的短样例。

## 常见坑

1. 写成过程流水账（「本周开了 3 次会」）→ 改成「计划 vs 实际 vs 差异 vs 原因」，读者只关心偏差。
2. 数字没有口径与期间 → 老板第一个问题就卡住；每个数字后面加括号写口径与时间范围。
3. 风险栏写「存在一定风险」→ 改成「触发信号 + 止损线」，否则等于没写。
4. 对外 BP 直接复用内部报告 → 泄漏内部代号与客户名；对外版单独写，脱敏后再发。
5. 让 AI 补 ROI → 它会编；只能让它在用户给的数据上算，并标出假设。
6. 一份文档同时服务「周报 + 立项 + 对外路演」→ 拆成三份，各自只保留需要的段落（`../modes/report.md` 的 section 删除测试）。
