# 职场沟通（Workplace Communication）

**什么时候读这个文件**：用户要写「在组织里发给具体人的东西」——邮件、IM 长消息、向上汇报、周报、述职/晋升答辩、跨部门沟通、拒绝、催办、道歉。
**读完你会得到**：职场沟通必须问的 8 个参数、3 种主力体裁骨架、留痕与敏感信息的边界，以及一个可直接用的「向上要资源」邮件提示词。
**分工**：报告类结构见 `./project-report.md`；说服与论证逻辑见 `../modes/report.md`。本文件只写组织关系、语气与留痕这些行业特有的东西。

## 什么时候用

- 用户会说：「帮我写封邮件」「这个话怎么跟老板说」「述职 PPT 的讲稿」「帮我回复同事这段消息」。
- 沟通对象有权力差（上级/客户/甲方/跨部门负责人），说错要付代价。
- 内容涉及要资源、要排期、要免责、拒绝、催进度、承认失误——都属于高敏感沟通。
- 用户给了一段「我要表达的意思」，但情绪很重、逻辑很乱，需要先重排再发。

## 行业参数

| 维度 | 必须问到 | 用户不答时的默认 | 采访编号 |
|---|---|---|---|
| 收件人 | 是谁、什么层级、和你的关系、是否要抄送 | 直属上级，不抄送 | `I-G1` |
| 沟通目的 | 通知 / 请求 / 说服 / 拒绝 / 对齐 / 免责 | 请求 + 对齐 | `I-P1` |
| 组织文化 | 层级分明还是扁平、直白还是含蓄、中/英/双语 | 中文、中性偏正式 | `I-G1` |
| 事实要素 | 时间、数字、责任人、deadline | 缺的留空并标出，不编 | `I-P1` |
| 敏感程度 | 是否要留痕、是否可能被转发、是否涉及人事/法务 | 假设会被转发，写得可公开 | `I-G3` |
| 期望回复 | 要对方做什么决定、什么时候要 | 3 个工作日内回复 | `I-G2` |
| 篇幅与渠道 | 邮件 / IM / 正式文档 / 会议口头稿 | 邮件正文，≤300 字 | `I-G4` |
| 历史上下文 | 之前有没有沟通、有没有口头承诺 | 视为首次书面沟通 | `I-G5` |

## 常用体裁 × 3

### 1. 邮件（主题 + 结论 + 请求）

```
主题：{{动作 + 对象 + 时间}}（例：申请市场部增加 2 名实习生｜3/15 前）
{{称呼}}，
一句话结论：{{我需要什么 / 我建议什么}}。
背景（≤3 句）：{{为什么现在提这件事，带关键数字}}。
请求（可选项化）：{{方案 A / 方案 B}}，我建议 {{A}}，因为 {{理由}}。
时间与影响：请在 {{日期}} 前回复；如果延后，{{什么会被影响}}。
附件/参考：{{文件名 + 一句话说明}}。
{{落款}}
```

适合谁：需要「留痕 + 拿到明确答复」的人；主题行写好，回复率能差一倍。

### 2. 向上汇报 / 周报（结论先行版）

```
【结论】{{一句话：项目状态 + 是否需要老板介入}}。
【本期关键结果】{{2–3}} 条，每条：做了什么 → 结果数字 → 与目标的差距。
【风险】{{1–2}} 条：风险是什么 → 会影响到什么 → 我打算怎么处理 → 需要谁配合。
【下期计划】{{2–3}} 条，带交付物与时间。
【需要决策】只在有时写：{{选项 + 我的建议 + 不决定的后果}}。
```

适合谁：上级时间少、需要在 60 秒内判断要不要介入的场景；核心是「结论和风险顶到最上面」。

### 3. 述职 / 晋升答辩（讲稿 + 结构）

```
【定位】{{岗位 + 层级 + 我要争取什么}}。
【一年做了什么】{{3}} 个项目，每个用 STAR：情境（S）→ 任务（T）→ 我做的事（A）→ 结果（R，带数字）。
【能力证明】{{2–3}} 条与目标岗位要求一一对应的能力，每条有 1 个具体事例。
【不足与改进】写 1 条真实的不足 + 已经做了什么；不写「我太追求完美」。
【下一阶段规划】{{3}} 条，与公司/部门目标挂钩，带可衡量指标。
【可能的质疑】评委最可能问的 3 个问题 + 我的回答要点。
```

适合谁：要评职级、拿晋升名额、做年度述职的人；评委听的是「证据 → 能力 → 匹配度」。

## 术语与合规边界

**必用术语（首次出现给中英对照）**

- 结论先行（BLUF, Bottom Line Up Front）、金字塔原理（Pyramid Principle）。
- STAR 法则（Situation-Task-Action-Result）：述职与面试的标准叙事。
- 目标与关键结果（OKR, Objectives and Key Results）、关键绩效指标（KPI）。
- 干系人（stakeholder）、对齐（alignment）、抄送（cc）、留痕（written record）。
- 述职（performance review）、晋升答辩（promotion review）、复盘（retrospective）。

**合规红线（职场沟通最容易踩）**

- **假设邮件会被转发**：写的时候问一句「这段话被我的老板、对方老板、HR 看到，是否还成立」。情绪化表达、指责个人、泄露他人评价，一律去掉。
- **不当承诺不写**：时间、价格、赔偿、责任归属，未经授权不在邮件里替公司承诺；用「我确认后回复」替代。
- **法律/人事争议走正式渠道**：涉及劳动纠纷、处分、竞业、诉讼风险，邮件里只陈述事实，不做责任认定，先同步法务/HR（细则见 `./legal.md`）。
- **不泄露**：客户名单、合同金额、未公开财务数据、同事个人隐私（薪资、健康、家庭）不入正文，必要时脱敏。
- 拒绝要写清「不做什么 + 为什么不 + 替代方案」，不写「这个做不了」就完事。
- 道歉信只描述事实与补救动作，不在书面材料里扩大责任范围。

## 填好的示例

场景：项目要延期，需要向总监申请追加 2 名人力，同时把上线时间从 3/20 推到 3/27。直接可用。

```
你帮我写一封发给总监的邮件，目标是：申请追加 2 名开发 + 把上线从 3/20 顺延到 3/27。

## 我的身份与关系
我是该项目负责人，直接向这位总监汇报；平时沟通偏直接。他关心两件事：会不会影响季度收入、需不需要他出面协调。

## 事实（只能用这些数字，不要补充）
- 原计划 3/20 上线，当前完成度约 70%（后端接口 12/16，前端 6/9 个页面）。
- 缺口原因：需求在 2/28 变更过一次（客户要求增加对账模块），我们当时评估"影响约 1 周"，实际影响了 2.5 周。
- 若不加人：3/27 上线，季度内仍能赶上 3/31 的验收；若加 2 人：可回到 3/23 上线，但需要 3/10 前到位。
- 延期影响：客户验收会从 3/25 挪到 3/31，季度收入不受影响，但市场部的推广排期要顺延一周。

## 邮件要求
1. 主题行 ≤20 字，包含动作和时间。
2. 第一句就是结论：我申请什么、需要他做什么决定。
3. 正文 ≤250 字，结构：结论 → 现状与原因（承认评估偏差，不甩锅）→ 两个方案对比（加人 / 不加人）→ 我建议哪个 → 需要他在什么时间前回复。
4. 给两个可选方案，每个都写清代价；不要只给一个"必须加人"的姿态。
5. 语气：承担该承担的（需求变更时我们低估了影响），但不自我贬低；不用「非常抱歉打扰您」这类过度客套。

## 边界
- 不承诺「加了人一定能按期」；写成「按当前进度排期估算」。
- 不出现客户真实名称，写「A 客户」。
- 不评价其他部门（比如市场部）；只陈述排期影响。
- 不发散到责任认定；这封邮件会被转发给他的上级，按可公开的标准写。
```

> 这段为什么这样写：把这些约束提前说出来，模型就不会给你一封「跪求支持」的信；「假设会被转发」是最有效的职场写作检查；主动承认评估偏差但不扩张责任，是向上沟通里最难的平衡点，必须在提示词里点名。
> 换模型：需要更严谨的书面语时给推理模型，只留目标、事实、边界，让它自己组织；小模型要把结构与字数硬编码进提示，否则会写成长篇。

## 常见坑

1. 主题行写成「关于项目进展的说明」→ 总监不会点开；改成「动作 + 对象 + 时间」。
2. 把情绪写进邮件（「已经催了三次了」）→ 改成「自 X 日起共催办 3 次，最近一次为 Y 日，目前无回复」，用事实施压。
3. 请求没有 deadline 和选项 → 对方只能拖着；给「A/B 方案 + 请在某日前回复」。
4. 述职只列苦劳（做了什么）不给结果数字 → 评委只认「结果 + 与目标岗位的匹配度」。
5. 在邮件里替公司做承诺（交期、赔付、价格）→ 先写「我确认后回复」，别留把柄。
6. 用「帮我写得专业一点」当指令 → 空话；改成「结论先行、正文 ≤250 字、给两个方案」这类可执行约束。
