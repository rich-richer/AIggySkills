# 科技与产品（Tech & Product）

**什么时候读这个文件**：用户要写产品与技术相关的文档——需求文档、技术方案、发布说明、竞品功能对比、路线图。
**读完你会得到**：产品类需求必须问的 7 个参数、3 种交付骨架、版本与安全类红线，以及一个可直接填写的 PRD 提示词。
**分工**：抽取类任务（从会议记录/用户反馈中提需求）见 `../modes/extraction.md`；操作类（部署、排障）见 `../modes/procedure.md`。

## 什么时候用

- 用户会说：「写个 PRD」「这个需求帮我拆一下」「技术方案怎么写」「发布说明（release notes）帮我整理」。
- 读者既有工程师也有管理层，同一份文档要同时满足「能开发」和「能决策」。
- 内容涉及版本、接口、数据结构、性能指标——**这些是幻觉高发区**，必须锁来源。
- 用户只给了一句需求（「做个会员体系」），没有场景与验收标准。

## 行业参数

| 维度 | 必须问到 | 用户不答时的默认 | 采访编号 |
|---|---|---|---|
| 产品阶段 | 0→1 验证 / MVP / 增长期 / 维护期 | MVP，先验证核心流程 | `I-G1` |
| 目标用户与场景 | 谁在什么情境下用、现在怎么凑合解决的 | 由用户提供 1 个真实场景 | `I-G1` |
| 技术栈与版本 | 语言/框架/中间件版本、部署环境 | 不写版本号，标「待确认」 | `I-O1` |
| 约束与不做范围 | 性能/成本/合规/人力/交付时间；本期明确不做什么 | 无硬约束，按最小可行实现；不做范围必须显式列出 | `I-G3` / `I-P1` |
| 验收标准 | 什么算完成（DoD）、谁来验 | 每条需求给可测的验收标准 | `I-G2` |
| 读者与用途 | 评审用 / 开发用 / 对外发布用 | 内部评审用 | `I-G4` |

## 常用体裁 × 3

### 1. 产品需求文档（PRD）

```
【背景与问题】{{谁在什么场景遇到什么问题}}，证据：{{用户反馈/数据，带来源}}。
【目标】{{1}} 个可衡量目标（指标 + 当前值 + 目标值 + 时间）。
【用户故事】作为 {{角色}}，我希望 {{能力}}，以便 {{价值}}。
【需求清单】{{P0/P1/P2}} 分级，每条含：描述、验收标准、边界情况。
【不做范围】本期不做：{{}}。
【风险与依赖】{{依赖的系统/团队/第三方}}，联调时间。
```

适合谁：要过评审、要交给工程开工的产品经理；验收标准写不出来就等于没写需求。

### 2. 技术方案（Design Doc）

```
【问题与约束】{{要解决的性能/架构问题}}，当前指标 {{数值}}，目标 {{数值}}。
【方案】主方案概述 + 关键数据结构/接口（含字段与类型）。
【权衡】对比 {{2}} 个备选方案：复杂度、成本、风险、迁移代价。
【风险与回滚】{{3}} 个失败模式 + 触发信号 + 回滚步骤。
【验证】压测/灰度/监控指标与阈值。
```

适合谁：要说服团队接受一个架构改动、并且要为上线失败负责的工程师。

### 3. 发布说明（Release Notes）

```
【版本】{{vX.Y.Z}}，发布日期 {{}}，影响范围 {{哪些端/用户}}。
【新增】{{功能 + 用户可见的变化}}。
【修复】{{问题 + 现象 + 影响版本}}。
【破坏性变更】{{变更点 + 迁移步骤 + 不迁移的后果}}。
【已知问题】{{问题 + 规避办法}}。
```

适合谁：对客户/内部使用方发版的人；破坏性变更不写清，第二天全是工单。

## 术语与合规边界

**必用术语（首次出现给中英对照）**

- 产品需求文档（PRD, Product Requirements Document）、定义完成（DoD, Definition of Done）。
- 用户故事（user story）、验收标准（AC, Acceptance Criteria）、最小可行产品（MVP）、技术债（tech debt）。
- 灰度发布（canary release）、回滚（rollback）、服务等级目标（SLO）、幂等（idempotence）。
- 个人可识别信息（PII）、个人信息保护法（PIPL）、应用编程接口（API）。

**合规红线**

- **不谎报接口与库行为**：模型对 API/版本容易编；要求「不确定的写『需核对官方文档』」，绝不允许凭记忆写函数签名。
- 不写真实密钥、账号、内网地址、客户数据（用 `<token>` 占位）；涉及用户数据的功能写清：收集什么、存哪、谁能看、保留多久（对应 PIPL 的最小必要原则）。
- 开源依赖写清许可证（MIT/Apache/GPL 的传染性不同），商用前需法务确认。
- 不做合规保证（「已符合等保」「GDPR 合规」）——这类结论须由合规/法务出具，AI 只能列检查项（待核实）。
- 性能/成本数字只能是实测或标注「估算」，不写成既成事实。

## 填好的示例

场景：给内部客服系统加「工单自动分类」。可直接改字段使用。

```
你帮我写一份 PRD，读者是 3 名后端 + 1 名前端 + 产品总监，评审会 30 分钟。

## 背景（只用我给的事实）
- 客服每天新工单约 400 单，目前人工分派到 6 个小组，平均首次分派耗时 11 分钟，错派率约 8%（2026-09 运营台账）。
- 错派会导致二次转派，平均多花 25 分钟。客服组长希望把首次分派压缩到 2 分钟内。

## 需求
做「工单自动分类 + 推荐分派小组」，人工可一键改判。范围只做分类与推荐，不做自动回复、不做自动关闭。

## 你要产出
1. 目标：1 个可衡量指标（分派耗时 p50 从 11 分钟降到 X 分钟）+ 1 个护栏指标（错派率不得高于当前 8%）。
2. 用户故事 3–5 条（客服组长 / 一线客服 / 系统管理员各 1 条以上）。
3. 需求清单分 P0/P1/P2，每条必须带验收标准（可测、可判）。
4. 边界情况：工单内容为空、含多语言、同一客户重复提交、模型置信度低时怎么处理。
5. 不做范围：明确列出本期不做的 4 项。
6. 风险与依赖（模型服务不可用时的降级路径）+ 数据与隐私（工单里有手机号与订单号，写清脱敏与保留策略）。

## 边界
- 不确定的接口、模型能力、字段名，一律写「需核对官方文档/需与后端确认」，不要凭印象编造。
- 不承诺准确率数字（写成「待用历史工单离线评估」并给出方法）；不写具体密钥与真实客户数据。
- 不给出「已符合个人信息保护要求」这类结论，只列检查项。
- 格式：Markdown；需求清单用表格（编号/级别/描述/验收标准/备注）；中文，术语首次出现给中英对照。
```

> 这段为什么这样写：把「不确定就写需核对」写进边界，是产品文档里唯一能压住 API 幻觉的办法；护栏指标（错派率不得变差）防止模型只优化主指标；把隐私与降级路径列成必答项，评审时才不会被当场问倒。
> 换模型：推理模型只给目标、范围、边界；小模型必须给固定表头 + 1 条填好的示例行。

## 常见坑

1. 把需求写成功能清单（「做一个筛选器」）→ 没有用户场景；每条需求前补「谁在什么情况下需要」。
2. 不写验收标准 → 开发和测试各自理解，最后返工。
3. 版本号/接口凭印象写 → 幻觉重灾区；一律标「需核对官方文档」。
4. 技术方案只给一个方案 → 没有权衡就没有说服力；至少写 2 个备选与选择理由。
5. 发布说明漏掉破坏性变更 → 客户升级炸锅；破坏性变更必须单列 + 迁移步骤。
