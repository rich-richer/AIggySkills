# 蒸馏成 Skill（distill-to-skill）

你的工作是把**一份来源**（书、资料、视频、课程）或**一段经验**（你刚和用户做完的任务）
转换成一份**下次同类任务能直接用的判断规则集**，而不是一份"关于这份来源的总结"。

> 蒸馏（Distillation）在这里不是训练小模型，而是整理一套 AI 做任务时能读取的
> 说明、示例和必要资料。它有没有用，不看压缩了多少字，而看下次碰到同类任务能不能真的用起来。

## 五条铁律

1. **先有任务，再提炼。** 没有"这份资料要解决什么具体问题"，就不许开始提炼。否则产出必然是「倾听、共情、识别需求」这类听着都对、明天用不上的东西。
2. **每条规则可溯源。** 每条规则必须标注来源类别：`[原文]`（资料明确写的，带位置）、`[AI补充]`（为你场景补的）、`[我的经验]`（用户在实际任务中确认的判断）、`[单次]`（只属于这一次的条件）。不标源 = 默认 `[AI补充]`，而 `[AI补充]` 不得进入通用规则。
3. **单次不等于通用。** 一次成功只证明"这次成立"。任何"这次客户预算有限""这次工期紧"之类的条件，一律降级为案例，不得写成"以后必须"。
4. **不把一切拆成步骤。** 有些资料给的是**观察角度**（perspective），有些是**判断框架**（judgment framework）。这类只保留**适用范围**，不要伪造操作步骤。
5. **没有验收标准就不算 Skill。** 每份产出的 skill 必须回答："什么样算做对了"以及"怎么证明它可复用"。

## 流程

### Phase 0 · 判定来源类型

| 来源 | 走向 | 主要风险 |
|---|---|---|
| 书 / 文章 / 视频 / 课程 | Phase 1A → 2A | 把 AI 的临时发挥当成原文方法 |
| 用户刚做完 / 正在做的工作 | Phase 1B → 2B | 把单次特殊要求写成永久规则 |

两类都有时（例如视频 + 用户自己的实践），**先做 A 再做 B**，B 阶段用 A 的框架去核对。

### Phase 1 · 定任务（10 分钟内完成）

写出**目标句**，缺一项就回去问：

```
我想用 [这份来源] 帮 [谁] 在 [什么时机] 判断/完成 [什么具体动作]，产出 [什么结果]。
```

- 反例：「帮我总结这本书。」→ 没有谁、没有时机、没有动作。
- 正例：「我想用这份资料帮销售在报价之前判断客户需求有没有问清楚，产出一份可追问的缺口清单。」

然后写**验收句**：`做到什么程度算合格？不合格的典型表现是什么？`

### Phase 2 · 提炼

- **2A 资料型**：读 [references/source-route.md](references/source-route.md)。产出五问清单 + 带出处的规则草稿。
- **2B 经验型**：读 [references/experience-route.md](references/experience-route.md)。从刚完成的对话里抽出"输入 → 判断 → 纠正 → 验收"。

### Phase 3 · 三类分流（决定性环节）

读 [references/rule-triage.md](references/rule-triage.md)，把草稿里的每一条投进三类：

| 类别 | 判定 | 去向 |
|---|---|---|
| 每次都要检查的标准 | 无条件成立、可逐条检查 | 写进 `## 判断规则` 的「必查」 |
| 视情况选择的做法 | 需要条件才能判断 | 写成 `IF … THEN … ELSE …` 分支 |
| 只属于这一次的信息 | 换个人/客户/主题就不成立 | 降级到 `## 示例` |

**分流错误是这份 skill 最常见的失败模式**，必须逐条过一遍并给出判定理由。

### Phase 4 · 试跑与验证

读 [references/acceptance.md](references/acceptance.md)。最低要求：

1. **旧案例回归**：用提炼时的那份原始案例再跑，确认仍能复现。
2. **新案例迁移**：换一个真实案例（换客户/主题/素材），确认没有明显掉点。
3. **缺口检测**：让它面对一份信息不全的输入，看是否**指出缺口**而不是脑补。
4. **越界检测**：看它是否把 `[单次]` 内容当作通用规则使用。

任一项不通过 → 回到 Phase 3，不要靠加一句"请注意"糊过去。

### Phase 5 · 写成 SKILL.md

按 [assets/skill-template.md](assets/skill-template.md) 落盘。目录约定：

```
<skill-name>/
├── SKILL.md            # 必需：frontmatter(name/description) + 判断规则 + 步骤 + 验收
├── references/         # 可选：细节、清单、判定表
├── assets/             # 可选：模板、示例
└── README.md           # 可选：给人看的用法与安装说明
```

硬性要求：

- `description` 写清**什么时候用**（触发词要具体），因为它决定了这个 skill 会不会被正确调用。
- `## 判断规则` 必须按三类分组，每条带来源标记。
- `## 验收标准` 必须可被第三方执行，不能是"感觉对了就行"。
- 正文控制在 500 行内，长内容拆进 `references/`。
- 不要写"请自动成长"。成长来自记录（错在哪 / 为什么改 / 什么结果被接受）+ 回归检查，见 Phase 6。

### Phase 6 · 维护与发布

- **修订时**：每次修改都记 `错在哪 → 为什么改 → 什么结果被接受`，并判断该改**通用规则**还是只**补一个例子**。改完旧案例和新案例都要重跑。
- **发布到 GitHub**（用户明确要求时）：见 `README.md` 的发布章节，或在 skill 目录内执行：

```bash
cd <skill-name>
git init && git add -A && git commit -m "feat: add <skill-name> skill"
gh repo create <repo> --private --source=. --push   # 公开用 --public
```

## 输出契约

交付时必须包含以下四块，缺一不可：

1. **目标句 + 验收句**（Phase 1）。
2. **三类分流表**，每行带判定理由与来源标记。
3. **skill 文件**（按模板，可直接放进 `~/.agents/skills/` 或项目的 `.agents/skills/`）。
4. **验证记录**：旧案例结果 / 新案例结果 / 失败的检查项。

## 反模式（出现即停手重做）

| 反模式 | 症状 |
|---|---|
| 摘要冒充技能 | 产出全是观点，没有可执行的判断条件 |
| 万能模板 | 把某次成功的话术/句式固化，换场景即失效 |
| 无源规则 | 说不出这条规则来自原文哪一段、还是 AI 补的 |
| 只验一个案例 | 原案例好用就宣布成功，不换任务 |
| 咒语式成长 | 写"自动优化""请自我学习"，但没有记录与回归机制 |
| 过度拆解 | 把"观察角度"类资料硬拆成 8 个步骤 |

## 边界

- **上游取料用 `media-sourcing`**，并要求它交接 `integrity` 与 `defects`；没有取料记录的材料，先补取料再炼制。
- **本 skill 只负责 L3（提炼）与落盘**。结构（L1）与观点（L2）属于对话级动作，不在这里重复：L1 只切结构不评价，L2 每条结论带出处并标 `[明确]`/`[推断]`。
- 一次性的创意工作、没有验收标准的探索性任务，不适合做成 skill；做了只会得到空话。遇到这种请求，直接说明并建议改用 SOP 或提示词。
- 本 skill 不负责**验收标准本身是否合理**。标准定错，skill 会把错误固化并放大。标准涉及合规/财务/健康等高风险领域时，要求用户提供可核对的依据。
- 来源涉及付费内容或他人版权时，产出应提炼**方法**，不得大段复制原文；示例中的原文引用保持最小必要。
