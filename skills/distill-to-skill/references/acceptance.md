# 验收与回归：怎么证明这个 Skill 真的可用

「有没有用，不看压缩了多少字，而看下次碰到同类任务能不能真的用起来。」

## 四项必测

### 1. 旧案例回归（Regression）

- 输入：提炼时用的原始案例（原客户 / 原素材 / 原文）。
- 期望：**行为不退化**。原来能发现的缺口仍然发现，原来给的标准仍给。
- 记录：通过 / 部分通过 / 失败 + 失败点。

### 2. 新案例迁移（Transfer）

- 输入：换对象（新客户 / 新产品 / 新主题 / 新数据）。
- 期望：核心判断仍然成立；只在确实不适用的地方按条件规则切换。
- 反例：新案例上完全失效，或需要你重新解释一遍——说明规则没写清。

### 3. 缺口检测（Gap detection）

- 输入：**故意信息不全**的案例。
- 期望：明确指出缺什么、需要追问什么；**不得脑补**缺失信息。
- 这是最容易被忽略、也最能区分"方法"和"话术"的一项。参考判据：
  - 它有没有把客户没说过的需求自己补出来？
  - 它提出的问题是不是有信息增量？

### 4. 越界检测（Scope violation）

- 检查：是否把「示例」区的内容当作通用规则使用？
- 方法：给一个与示例条件不同的输入，看它会不会机械套用那个示例的数字/句式/结论。

## 验收记录模板

```markdown
## 验证记录（YYYY-MM-DD）

| 检查项 | 输入 | 结果 | 说明 |
|---|---|---|---|
| 旧案例回归 | 原客户 A 记录 | 通过 | 缺口识别 3/3 一致 |
| 新案例迁移 | 客户 B | 部分通过 | 漏了"预算区间"追问 |
| 缺口检测 | 只给 2 句话的记录 | 通过 | 明确列出 4 项缺失 |
| 越界检测 | 无预算信息客户 | 通过 | 未套用示例中的 8 万 |

结论：待修 1 项（迁移漏问）→ 回到 Phase 3 补 IF 条件
```

## 修订原则

- 每次失败先判断：**是规则错，还是例子少？**
  - 规则错 → 改通用规则，**必须重跑旧案例**（防止修好新问题、弄坏旧能力）。
  - 例子少 → 只补示例，不动规则。
- 不要因为一次失败就加"请注意""务必注意"这类软约束；软约束无法被验证。
- 记录三件事：**这次哪里做错 / 为什么改 / 什么结果被接受**。

## 反模式

| 反模式 | 后果 |
|---|---|
| 只在原案例上测 | 假阳性，上线即失效 |
| 用构造的完美样例测 | 测不出缺口检测能力 |
| 写"请自动成长"代替记录 | 无反馈、无回归，永远不进步 |
| 每次随手意见都变成永久规则 | 规则膨胀、互相冲突 |
