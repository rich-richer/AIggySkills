# 三类分流：决定一条规则能不能进通用区

这是整条流水线的**决定性环节**。分流错误，产出的 skill 就只是一次成功的话术模板。

## 判定三问

对草稿里的每一条，依次问：

1. **换一个对象还成立吗？**（换客户 / 产品 / 主题 / 项目）
   - 不成立 → `[单次]`，进「示例」
2. **它需要条件才能判断吗？**
   - 需要 → 「情境做法」（写 IF/THEN）
3. **它无条件成立、且可逐条检查吗？**
   - 是 → 「必查」（写进通用规则）

## 三类定义与写法

### A. 必查标准（Every-time check）

- 定义：无条件成立、每条任务都必须过一遍、可客观核对。
- 写法：祈使句 + 可观察证据。
- 例：`每条交付周期的承诺，必须给出依据来源（人/数据/合同条款）。`
- 反例：`交付周期要合理`（无法核对）。

### B. 情境做法（Conditional practice）

- 定义：正确做法取决于具体情况，必须写清触发条件。
- 写法：`IF <可观察条件> THEN <做法> ELSE <另一做法>`，并注明判断人。
- 例：
  ```
  IF 客户明确表示预算上限
  THEN 提供低价档 + 说明削减了哪些范围
  ELSE 按价值定价，先讲结果再讲价格
  判断人：销售负责人
  ```

### C. 单次信息（One-off case）

- 定义：只属于这一次的人/时间/预算/素材/主题。
- 写法：作为**示例**保留，必须写清"换场景时怎么改"。
- 例：`示例：某客户预算上限 8 万，因此方案砍掉了二期模块。——换客户时重新确认预算区间，不要沿用这个数字。`

## 危险信号清单

出现以下任一条，说明分流大概率错了：

| 信号 | 说明 |
|---|---|
| 规则里出现具体数字/人名/日期，但没写成示例 | 单次信息泄露进通用区 |
| 规则写成「一律」「必须永远」但没有依据 | 过度推广 |
| 规则里有"如果…"但没有明确判断标准 | 情境做法写成了必查 |
| 示例区只有成功案例，没有"这次为什么特殊" | 无法迁移 |
| 一条规则既想当必查又想条件成立 | 拆成两条 |

## 分流完成后

1. 逐条给出判定理由（一句话），写进交付物。
2. 统计比例：若「必查」超过 15 条，通常说明目标太泛，回去收窄。
3. 若「示例」为空，通常说明你还没做换场景验证，方法可能只是这一次的经验。
